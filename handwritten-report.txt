BST and Hash Table Performance

In this work, I compared a Binary Search Tree and a Hash Table. I implemented both structures in Java and tested insertion, searching and deletion with 100, 1,000 and 10,000 elements.
In my BST, smaller keys go to the left and larger keys go to the right. Its performance depends on the tree height. With random insertion order, operations take O(log n) time on average. However, my tree does not balance itself. Sorted input creates a long chain, so one operation can take O(n). The best case is O(1), for example, when searching for the root. Inserting into an empty tree or deleting a root with at most one child is also O(1).
My Hash Table uses a hash function to choose a bucket. If keys have the same bucket, they form a linked list. With a good distribution, searching and deletion take O(1) time on average. Insertion is amortized O(1), which means it is constant time on average over many insertions. Sometimes the table grows and moves all keys, which takes O(n). All three operations have an O(1) best case and an O(n) worst case because a collision list can become long.
I measured each batch nine times after warmup and used the median. With 10,000 randomly ordered keys, insertion took 0.6411 ms for the BST and 0.1746 ms for the Hash Table. Searching took 0.4579 ms and 0.0202 ms. Deletion took 0.4814 ms and 0.0277 ms. These are times for all 10,000 operations, not for one operation.
The Hash Table was faster in the normal test. Sorted insertion made the BST search batch rise to 99.1224 ms. When I forced all keys into one hash bucket, the Hash Table search batch took 82.8891 ms. This shows that the input can strongly change performance. Memory access, resizing and Java warmup also affect the results.
I would choose a Hash Table for fast exact-key searches when keys spread well. A BST keeps keys ordered, but a balanced tree is needed to avoid long chains. Neither structure is always faster in every situation.
